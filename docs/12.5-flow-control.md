# Flow Control

Credit-based per-stream flow control is the mechanism that
bounds in-flight data end-to-end and makes unbounded streams (live video in or
out) safe: a sender can never run further ahead of its receiver than the
granted window.

## The laws

- **L9** — The credit unit is one CHUNK frame. A sender holds a per-stream
  window initialized to the negotiated `initial_credit` (default 32 chunks ≈
  8 MiB at the default `max_chunk`); each CHUNK sent decrements it; at zero
  the sender MUST wait (async or blocking, per language).
- **L10** — The receiving **endpoint** grants credit by sending a CREDIT frame
  after consuming chunks; grants are batched (recommended trigger: consumed ≥
  window/2). **Flush-before-block corollary:** a party holding pending
  sub-batch grants MUST flush them before ANY blocking wait — an empty-input
  recv, a quiet poll tick, or a downstream credit acquire (forwarders grant
  upstream and acquire downstream; blocking on either while holding grants
  can starve the very producer that would unblock the chain). Batch thresholds are derived from the receiver's own link
  negotiation, while the sender's window may come from a different link — a
  sender can therefore legally stall below the receiver's batch threshold, and
  only the flush guarantees progress under any window/batch mismatch. Granted credit is a **buffer guarantee**: the receiver must hold
  queue capacity ≥ its outstanding grants, so data frames can never block the
  delivery of control frames. This is the deadlock-freedom invariant that lets
  bounded-queue implementations (Go, Python) participate safely; the Rust
  reference keeps unbounded internal channels and enforces the window by
  count instead — same wire-visible law.
- **L11** — Credit is end-to-end. Intermediaries (host runtime, relay switch)
  forward CREDIT frames along the request's route exactly like Cancel; they
  never originate or absorb credit.
- **L12** — Receiving a CHUNK beyond the granted window is a fatal protocol
  error: the receiver fails the request with `CREDIT_VIOLATION`.
- **L13** — A request terminal (END/ERR/Cancel) releases all credit waiters
  with an error, promptly. A sender blocked on credit must never hang.
- **L14** — Credit applies in both directions — engine→cartridge input
  streams (the cartridge's `InputStream` consumption grants), cartridge→engine
  output streams (the executor's consumption grants), and peer↔peer argument /
  response streams. LOG, ERR, END, STREAM_START, and STREAM_END are never
  credited: progress and errors always flow, even when data windows are
  exhausted.
- **L15** — An endpoint that sends and receives on the same request MUST
  service inbound frames concurrently with sending — a sequential
  send-then-collect loop deadlocks the moment a handler produces output while
  its input is still flowing.

## Wire elements

| element | value |
|---|---|
| CREDIT frame type | 13 (non-flow: no seq, bypasses reorder buffers) |
| `credit` key | 19 — u64 grant, in CHUNK units |
| grant target | (rid, `stream_id`); a grant without `stream_id` credits the request's sole registered stream |
| `credit_dir` meta | `"request"` or `"response"` — which side's stream is credited. MANDATORY: hosts route grants by it (a `response` grant travels toward the handler, a `request` grant toward the requester); the (xid, rid) key alone is ambiguous for self-loop peer calls. A direction-less grant is an unroutable counted drop. |
| `initial_credit` | negotiated in HELLO / RelayNotify limits, element-wise min, default 32 |

## Reference implementation map (Rust)

- `capdag/src/bifaci/credit.rs` — `CreditGate` (replenishable window:
  `acquire`/`blocking_acquire`/`grant`/`close`) and `CreditRouter` (delivers
  inbound CREDIT frames to registered gates; `close_request` releases a
  request's waiters, L13). Built on mutex + notify so the semantics translate
  directly: Python `threading.Condition` over an int, Go token channel, Swift
  continuation queue.
- Cartridge output: `OutputStream::write` / `emit_list_item` / `emit_cbor` are
  `async` and acquire one credit per chunk; `blocking_write` /
  `blocking_emit_list_item` serve FFI threads; `StreamSender` (detached
  emitter) acquires blocking-ly. Gates register with the runtime's router on
  `start()`; the run loop routes inbound CREDIT frames to them and closes them
  on handler completion or Cancel.
- Cartridge input: the demux tracks a per-stream window
  (`initial_credit` + grants); `InputStream::recv` emits batched grants as the
  handler consumes (window/2). An over-window chunk surfaces as a
  `CREDIT_VIOLATION` stream error (L12).
- Engine: `send_one_stream` registers a gate per input stream and acquires per
  chunk; `collect_terminal_output` / `TerminalOutput` grant for consumed
  response chunks and route inbound CREDIT frames to the send gates
  (`CreditPlumbing`). `execute_fanin` runs input-feed and response-collect
  concurrently (L15).
- Pipelined chains (`forward_frames`, both the reference executor and the
  machfab engine): every hop acquires from the downstream cap's window and
  grants the upstream cap as it consumes.

## What is deliberately NOT flow-controlled

LOG/progress frames (L14). A stalled data window must never silence progress
reporting — TEST7062 asserts it. The unbounded-LOG risk is accepted and
observable via the drop counters.

## The teardown race, and how unroutable frames are classified

Credit crosses the wire in the opposite direction to the chunks it credits,
so a grant can always be in flight when the request's terminal lands — two
sockets, opposite directions; no sender-side check can close the window.
Receivers therefore discriminate every unroutable frame two ways — and the
two outcomes are DIFFERENT KINDS of event, counted in different families
(see the `stats` module: `StragglerCounters` vs `DropCounters`):

- **Benign post-terminal straggler** — the frame's RID belongs to a
  RECENTLY TERMINATED request: it crossed END/ERR in flight. This is the
  ordinary, protocol-legal teardown race of credit-based flow control (a
  grant, a duplicate terminal, a straggling LOG, a callee that ENDed
  before draining its input). Nothing went wrong and no data was lost —
  the frame is moot. It is NOT a drop: it is counted in the straggler
  counters, per frame type (so a trace says "late credit" vs "late
  chunk"), logged at debug level, and indicated as benign in every stats
  surface (`stragglers` beside `drops` in snapshots and traces,
  `stragglers_total` beside `drops_total` on heartbeats).
- **`no_route` drop** — the runtime has never known the RID. A genuine
  routing anomaly worth alarming on: counted in the drop counters
  (per reason × frame type) and logged as a warning.

The discriminator is the bounded recently-terminated ring every routing
runtime already keeps (64 entries — the relay switch's request table ring,
the hosts' terminal-released ring). The race window is milliseconds, so ring
eviction cannot misclassify a real race; a pathologically late frame ages
back into `no_route`, where something that stale belongs. GC-evicted routing
entries are deliberately NOT in the ring: an evicted entry never saw its
terminal, so its frames are real routing loss.

Sender-side gates exist too, and are exactly two: the relay switch hard-errors
`UnknownRequest` back to direct API callers (the engine must observe that a
request no longer exists and stop sending), and the engine's upstream-credit
sender treats exactly that error as moot — credits for a finished request
carry no meaning, and failing a body for one would turn the teardown race into
a spurious execution failure. Every other send failure stays hard.

## The stats ledger is a window

The per-stream `credit_outstanding` in protocol-stats snapshots is the
stream's REMAINING WINDOW as observed by that runtime: seeded with the
request's destination-negotiated `initial_credit` when the stream's ledger
entry is created, minus one per CHUNK in either direction (a stream's chunks
all flow one way; its grants flow the other), plus each grant's count.
Engine-originated outbound frames are recorded in the same ledger at the
switch's send path. Non-negative in healthy operation; a negative value
means the producer overran its window. Diagnostic — the endpoints hold the
authoritative windows.
