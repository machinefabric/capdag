# 18.1 — The `capdag` CLI Reference

`capdag` is both the reference implementation of this specification and a
command-line **product**: a Unix-style tool that runs a single cap, runs a whole
`.machine` graph, inspects the fabric, and scaffolds and develops cartridges.
Every mode drives a real bifaci host with the bundled cartridges registered, so a
cap's peer calls (model downloads, fabric lookups) work exactly as they do inside
the engine.

## Fabric binding

Every `capdag` invocation resolves caps, media, and aliases against **one** fabric
registry. A shipped binary bakes that registry's URL at build time
(`CDG_FABRIC_REGISTRY_URL`); a runtime environment variable of the same name
overrides the baked value. The schema base (`CDG_SCHEMA_BASE_URL`) is only ever
paired with the fabric URL, never split. This is what makes a `--staging` build
resolve `disbind-pdf` against the staging fabric rather than production.

## Commands

```
capdag <cap-alias-or-urn> [cap args] [inputs...] [options]   Run one cap
capdag run <machine-file> [inputs...] [options]              Run a .machine file
capdag dag-viz <machine-file> [--mermaid|--dot]              Render the execution plan
capdag find <cap-alias-or-urn>                               Show the providing cartridge(s)
capdag resolve [--no-cache] <cap-alias-or-urn>...            Print cap definition JSON (array for >1)
capdag cache [clear|refresh]                                 Invalidate/renew the local fabric cache
capdag install <cap-alias-or-urn-or-cartridge-id>            Download + verify without running
capdag new <name> [--python] [-o <dir>]                      Scaffold a new cartridge project
capdag dev-install <project-dir>                             Install/update a dev cartridge under the dev slug
```

### `capdag <cap> …` — run one cap (single-cap mode)

The default mode: a bare cap alias or URN is run as a Unix-style tool, driving the
cap's **own** declared interface.

- Piped stdin, or input file path(s), feed the cap's stdin arg.
- The cap's declared `--flags` and positional args are accepted natively.
- `--arg <name-or-media-urn>=<value>` addresses any arg explicitly (repeatable;
  `@<path>` reads a file's bytes for a binary arg).
- **Output (pipe discipline):** a single scalar result streams RAW to stdout;
  sequences and fan-outs write files (`{input}.{node}[.{i}].{ext}`) and list their
  paths on stdout. Logs and progress go to stderr.

**Abstract caps** (dispatch umbrellas like `disbind`, `convert-image`) are narrowed
here: `capdag` resolves the alias to the abstract cap, detects the input media, and
narrows to the concrete cap via `is_dispatchable` (see
[07-DISPATCH](/docs/07-dispatch) §"Abstract caps"). An ambiguous target is
resolved with `--to <ext|media-urn>`; an unresolvable one fails hard.

**Local dev fallback.** If the token names a cap the fabric does **not** define,
`capdag` falls back to a locally dev-installed cartridge's own manifest (run by
its alias) and runs that cap through the full host — provided the cap does not
conflict with the fabric (no alias of it already means a different cap upstream).
This is what lets a brand-new cap be developed and run before it is ever
published. See [18.2 — Getting Started with Cartridge Development](/docs/18.2-getting-started-cartridge-development).

### `capdag run <machine-file> …`

Run a `.machine` data-flow graph. Inputs and the same options as single-cap mode
apply; ForEach/Collect and fan-out are planned and executed by the shared
orchestrator.

### `capdag dag-viz <machine-file> [--mermaid|--dot]`

Render the machine's full execution plan (`MachinePlan`) as a diagram —
ForEach/Collect/Merge/Split/InputSlot/Output nodes and typed edges, not a flat
DAG. `--mermaid` (default) emits Mermaid; `--dot` emits Graphviz DOT.

### `capdag find <cap-alias-or-urn>`

Resolve a cap and print which registry cartridge(s) provide it (and whether a
signed binary is available for this platform), without downloading anything.

### `capdag resolve [--no-cache] <cap-alias-or-urn>...`

Print the cap's canonical definition JSON, resolved through the baked fabric
registry — the same definition every mirror uses. Cartridges use this to
(re)generate the cap-def snapshots they embed. Passing **several** tokens prints
a JSON **array** of cap defs (one process, one manifest read) — cartridge snapshot
generation resolves a whole `cap-aliases.txt` in a single batched call this way.
`--no-cache` forces a fresh fetch, bypassing the version-keyed on-disk cache
(which a mutable staging channel can leave stale).

### `capdag cache [clear|refresh]`

Manage the version-keyed local fabric cache. `clear` purges it (in-memory and
on-disk, manifest included); `refresh` (the default) purges and then re-fetches
the manifest so the next command starts renewed. Use it after a channel
re-publishes under the same manifest version.

### `capdag install <cap-alias-or-urn-or-cartridge-id>`

Resolve, download, and verify a cartridge (signature chain + hashes) without
executing anything — a cache warm-up. Prints the installed binary path.

### `capdag new <name> [--python] [-o <dir>]`

Scaffold a fresh cartridge project into `<dir>/<name>/` (default `<dir>` is the
current directory). Python is the only (and default) kind today. Writes a runnable
`cartridge.py`, a `README.md`, and a `.gitignore`. `<name>` must be a path-safe,
lowercase slug (`[a-z0-9]` with `-`/`_` separators). See [18.2](/docs/18.2-getting-started-cartridge-development).

### `capdag dev-install <project-dir>`

Install — or update — a dev cartridge under the per-user cartridge root's reserved
`dev` slug, so the host discovers it. `capdag` reads the project's manifest (by
running its entry's `manifest` subcommand), verifies that none of its caps
conflict with the fabric, then stages it at
`~/.capdag/cartridges/dev/v{CARTRIDGE_REGISTRY_VERSION}/{channel}/{name}/{version}/`
with a `cartridge.json` install record (`registry_url: null`). Re-running
overwrites the same version directory — the update step of the edit/reinstall
loop. `<project-dir>` defaults to `.`.

## Global options

| Option | Applies to | Meaning |
|--------|-----------|---------|
| `-o, --output <dir>` | run, single-cap, new | Output directory (run modes) / project parent (`new`) |
| `--force` | run modes | Overwrite existing output files |
| `--arg <name>=<value>` | single-cap | Explicit cap argument (repeatable) |
| `--to <ext\|media-urn>` | single-cap | Target output for narrowing an abstract cap |
| `--dev-bins <binary>…` | run modes | Host local cartridge binaries directly |
| `--trace <file.trace>` | run modes | Write a per-segment bifaci protocol trace (JSONL) |
| `--help`, `-h` | any | Show usage |

## The per-user cartridge root

`capdag` hosts cartridges from `~/.capdag/cartridges/`, using the **same**
registry-, version-, and channel-partitioned tree every host uses:
`{registry_slug}/v{CARTRIDGE_REGISTRY_VERSION}/{channel}/{name}/{version}/`. The
`dev` slug is reserved for locally built cartridges (`registry_url: null`); see
[16.1 — Cartridge Anatomy](/docs/16.1-cartridge-anatomy) for discovery and the
slug/version layout.
