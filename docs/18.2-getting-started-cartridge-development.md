# 18.2 — Getting Started with Cartridge Development

This guide builds a cartridge from nothing to a running capability, using the
`capdag` CLI to scaffold it, install it locally, run it, and iterate. The whole
loop — **create → install → run → change → update** — happens on your machine; a
dev cartridge never has to be published to be developed and run.

We build **sentiment-tagger**: a cartridge that reads text on stdin and emits
`positive`, `neutral`, or `negative` from a small word-list rule. No model, no
network — it demonstrates every required piece of the cartridge contract.

## Prerequisites

- **Python 3.12+** and the cartridge runtime on PyPI:

  ```bash
  pip install capdag        # pulls the capdag Python runtime + the ops framework
  ```

  The scaffolded cartridge is launched by the host through its
  `#!/usr/bin/env python3` shebang, so the `python3` on your `PATH` must be able to
  `import capdag`.
- The **`capdag` CLI** (this tool) on your `PATH`.

## 1. Create the project

```bash
capdag new sentiment-tagger --python
cd sentiment-tagger
```

This writes a runnable project:

```
sentiment-tagger/
  cartridge.py     # the cartridge — one custom cap, one Op, one manifest
  README.md
  .gitignore
```

`cartridge.py` is the whole cartridge. It:

1. Declares a **cap** — an (input media, operation, output media) triple named by a
   cap URN — plus the cap's `aliases` (the human names) and its stdin arg and
   output. The scaffold seeds the cap's alias and media tags from your project
   name, so they are unique and never collide with the published fabric:

   ```
   cap:in="media:enc=utf-8;sentiment-tagger-input";out="media:enc=utf-8;sentiment-tagger-tag";sentiment-tagger
   aliases = ["sentiment-tagger"]
   ```

2. Implements an **Op** (`TagOp.perform`) that drains the input, calls
   `classify()`, and emits the result.

3. Advertises the cap (and the mandatory `identity` cap) in a **manifest** with
   `registry_url = None` — the marker of a dev cartridge.

> **URNs are opaque.** The scaffold builds the cap URN once via `CapUrnBuilder` and
> registers the Op with the string derived from it — never a hand-written URN. The
> runtime canonicalizes tags alphabetically; a mismatch would fail dispatch.

You can inspect the manifest at any time — cartridges have a built-in CLI:

```bash
./cartridge.py manifest | python -m json.tool
```

## 2. Install it under the `dev` slug

```bash
capdag dev-install .
```

`capdag` reads the project's manifest, checks that none of its caps conflict with
the fabric, and stages the project under the per-user cartridge root:

```
~/.capdag/cartridges/dev/v1/nightly/sentiment-tagger/0.1.0/
    cartridge.json     # install record: registry_url=null, entry=cartridge.py
    cartridge.py
    ...
```

The `dev` slug is reserved for cartridges with no registry; `v1` is the baked
`CARTRIDGE_REGISTRY_VERSION`; `nightly` is the channel from the manifest.

### The no-conflict rule

A dev cartridge may declare caps the fabric has never heard of — that is the point
of local development. It just may **not** hijack a name the fabric already owns:
if any of its aliases already resolves, in the fabric, to a *different* cap,
`dev-install` (and a subsequent run) fails hard and tells you which alias
collided. Rename the alias and try again.

## 3. Run it

```bash
echo "I love this"     | capdag sentiment-tagger    # → positive
echo "this is awful"   | capdag sentiment-tagger    # → negative
echo "the sky is blue" | capdag sentiment-tagger    # → neutral
```

`sentiment-tagger` is **not** in the fabric, so `capdag` falls back to your locally
dev-installed cartridge's own manifest, injects its definition, and runs the cap
through the full bifaci host — exactly the path a published cap takes. You are
testing the real thing, not a simulation.

## 4. Change it and update the install

Edit `classify()` in `cartridge.py` — say, teach it a new word — then re-install:

```bash
capdag dev-install .
echo "the sky is blue" | capdag sentiment-tagger    # → positive (if you added "blue")
```

Re-running `dev-install` overwrites the same version directory, so the next run
picks up your change. That is the entire development loop: **edit → `dev-install`
→ run**, repeat.

To make a clean break, bump `version` in `build_manifest()` (e.g. `0.1.1`); the new
version installs alongside the old one, and the host picks the latest by version
sort.

## Adding a second cap

Each new cap needs three things, all in `cartridge.py`:

1. A new `Cap` in `build_manifest()` with a fresh operation marker, distinct
   input/output media URNs, and its own `aliases`.
2. A new `Op` subclass implementing the work.
3. A `runtime.register_op_type(<cap-urn-string>, <OpClass>)` call in `main()`,
   using the build-once-keep-the-string pattern so the byte form matches the
   canonicalized URN.

Cartridges with N caps are no different from one-cap cartridges; the runtime
dispatches on the request's cap URN against the table you registered.

## Publishing later

When a cap graduates from local development, its URN, media, and alias become
fabric definitions (authored in `fabric/caps/*.toml` and `fabric/media/`, published
through the cartridge registry). At that point the cap resolves in the fabric
directly and the local dev fallback is no longer involved — the same cartridge,
now installed under its registry slug instead of `dev`, provides a published cap.

## Troubleshooting

- **`… claims alias 'X', but the fabric already maps that alias to a different
  cap`** — your dev cap's alias collides with the fabric. Rename it.
- **`not defined in the fabric, and no dev cartridge … advertises it`** — the alias
  isn't published and no dev cartridge provides it. Check `capdag dev-install`
  succeeded and the alias matches the manifest.
- **`could not run the cartridge entry … to read its manifest`** — `cartridge.py`
  isn't executable or its dependencies aren't importable. Ensure `pip install
  capdag` ran for the `python3` on your `PATH`, and that `cartridge.py` is
  executable.
- **The handler isn't called (`NoHandlerError`)** — the URN you registered doesn't
  byte-match the dispatched URN. Build the URN once via `CapUrnBuilder` and reuse
  its `.to_string()`, as the scaffold does.
